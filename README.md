## Design Write-Up

### Problem Framing: Piecewise-Linear RUL Regression

**Chosen approach**: Regress a capped Remaining Useful Life (cycles to failure) for each pump-cycle observation.

**Why regression over classification or survival analysis:**
- The inference contract requires `predicted_rul` in cycles — a number the maintenance team can act on.
- Failure-within-window classification produces a probability, not a horizon. Converting it to a work-order requires a calibrated threshold the client hasn't provided.
- Survival models (Cox PH, Weibull AFT) are the theoretically ideal approach for censored data, but with 72 failure events and ~20 covariates, the statistical power for a fully parametric survival regression is marginal. We *use* survival concepts (Kaplan-Meier, censoring handling) without committing the full prediction pipeline to them.

**Why piecewise-linear (capped) RUL:**
Early sensor readings are statistically indistinguishable whether a pump will eventually live 100 or 400 cycles. Predicting "350 cycles remaining" from cycle 5 is asking the model to do something the data cannot support. Capping RUL at `RUL_MAX` (the empirically derived degradation onset point) encodes the operational reality: we only claim predictive value within the degradation window. This is standard practice in the PHM literature (NASA C-MAPSS benchmark).

### Censoring: The Critical Design Decision

8 of 80 pumps are right-censored (monitoring stopped while healthy). Treating them as failures assigns `RUL=0` at their last cycle — a silent label-poisoning error that would make a healthy pump look like a dying one.

**Correct handling:**
- Censored units receive `sample_weight=0` → excluded from the supervised objective.
- They are retained for feature engineering (their early-life baseline data is valid).
- Mann-Whitney U test confirms distributions are statistically indistinguishable at matched cycle windows → censoring is random (uninformative), validating the exclusion strategy.

### Feature Engineering: Physics-Informed, Not Kitchen-Sink

Features are organised in five physically motivated categories:

| Category | Rationale |
|---|---|
| Rolling statistics (mean/std/CV, 4 windows) | Captures local signal level and volatility — noise increases as mechanical looseness grows |
| OLS slope + curvature (3 windows) | Captures drift rate and acceleration toward failure |
| EWMA + deviation (3 alphas) | Noise-robust level tracking; deviation detects anomalous departures |
| Baseline z-score (vs own healthy first 20 cycles) | Removes unit-to-unit manufacturing variation; pure condition signal |
| Cross-sensor interactions | Physics: efficiency, pressure ratio, specific vibration |

~790 candidates → 150 selected via XGBoost gain importance + SHAP validation.

### Model Architecture: XGBoost + LightGBM Ensemble

**Why not LSTM/Transformer:**
With 72 training sequences, a deep sequence model has insufficient data to generalise. The bias-variance trade-off strongly favours low-complexity, high-regularisation models at this fleet size. The CNN/LSTM comparison in Notebook 04 confirms this empirically.

**Asymmetric loss:**
XGBoost is trained with the PHM Society asymmetric objective:  
- `L(d) = exp(-d/13) - 1` for early predictions (d < 0)  
- `L(d) = exp(d/10) - 1` for late predictions (d > 0)  

Late predictions are penalised ~30% more steeply, matching the business cost asymmetry: a missed failure costs far more than a false alarm.

### Validation: Unit-Level GroupKFold

GroupKFold(5) ensures no pump appears in both train and test within a fold. Feature engineering baselines are refitted on training folds only. This is the only honest estimate of generalisation performance.

## Output Contract

```csv
unit_id,predicted_rul,failure_prob_30,health_index,prediction_std,warning_level,last_cycle,n_cycles_observed
PUMP_T01,57.0,0.021,0.544,3.2,AMBER,312,312
PUMP_T02,14.3,0.891,0.886,1.8,RED,198,198
```

| Column | Description |
|---|---|
| `predicted_rul` | Estimated cycles to failure (PRIMARY scored output) |
| `failure_prob_30` | P(failure within 30 cycles) — from calibration curve |
| `health_index` | 0=healthy, 1=critical — continuous |
| `prediction_std` | Std of last-5 cycle predictions — confidence proxy |
| `warning_level` | GREEN (>60) / AMBER (31-60) / RED (≤30) |

## Known Limitations

| Limitation | Impact | Status |
|---|---|---|
| Fleet size (80 units) | Feature selection noise | Mitigated by conservative regularisation |
| RUL_MAX cap | Loses variation above cap | Acceptable for operational use |
| No concept drift detection | Degrades as fleet evolves | Future work |
| Sensor column auto-detection | May misclassify novel channels | Read data_dictionary.md, override in config |
